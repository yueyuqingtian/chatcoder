## 0. 摘要

WorkBuddy 是腾讯 **CodeBuddy** 的 OEM 桌面版（Electron 31 壳 + 内嵌 CodeBuddy Code CLI），统一网关为 `https://copilot.tencent.com`。把 WorkBuddy 登录后的自带模型作为新的模型供应商类型 **`workbuddy`** 接入当前项目：

- 用户在当前项目内完成 WorkBuddy 账号登录（复刻 CLI 的 `auth/state` -> 浏览器授权 -> 轮询 token 流程，与 ta3 的 PKCE 浏览器登录同构）；
- 自动拉取 `/v3/config` 产品配置（含 50 个模型的完整元数据：上下文窗口、推理档位、多模态、credits 倍率），同步为当前项目 Provider/Model 记录；
- 聊天请求由新增的 `WorkBuddyProvider` 发出：**标准 OpenAI Chat Completions 协议**（`POST {endpoint}/v2/chat/completions`，SSE 流式），注入网关鉴权/追踪头（`Authorization: Bearer` + `X-User-Id` + `X-Domain` 等）；
- **无需工具名伪装**：WorkBuddy CLI 对工具 schema 完全透传（标准 OpenAI function calling），比 ta3 接入更简单；
- **上下文管理、压缩、系统规则、编排仍完全沿用当前项目**（`agent_loop` / `context_manager` / `compaction` 不动）。

## 1. WorkBuddy 链路逆向分析（事实清单）

> 证据来源：`resources/app.asar.unpacked/cli/dist/codebuddy.js`（22MB CLI bundle，下称 **CLI bundle**）、`resources/app.asar.unpacked/cli/product.json`（产品配置）、`resources/app.asar`（桌面端主进程，下称 **桌面端**）、`~/.workbuddy/`（CLI 用户数据目录）。所有偏移量为逆向时的 bundle 字符位置，仅作证据索引。

### 1.1 产品身份与服务端点

`product.json`（CLI 静态产品配置，本地缓存同构）：

| 项 | 值 |
|---|---|
| productName | `WorkBuddy` |
| endpoint | `https://copilot.tencent.com`（生产）|
| stagingEndpoint | `https://staging-copilot.tencent.com` |
| 认证类型 | `cli-external-link`，id `workbuddy-desktop`，platform `workbuddy` |
| prefixPath | `/plugin`（认证接口前缀） |
| 内部域名 | copilot.tencent.com / www.codebuddy.cn / www.workbuddy.cn 等 |
| 海外域名 | www.codebuddy.ai / staging-codebuddy.tencent.com |

桌面端架构：Electron 主进程通过 sidecar（Windows 命名管道 `\\.\pipe\workbuddy-{hash}-sidecar-control`，JSON-RPC）管理 CLI 子进程；登录态由桌面端持有（VSCode 风格 secret storage，`state.vscdb` 中 `secret://...planning-genie.new.accessToken`，Electron safeStorage 加密），通过 `managedEnv` 注入 CLI。CLI 独立运行时的登录态落在 `~/.workbuddy/auth/{authentication.id}.info`（FileAuthenticationStorage）。

产品配置缓存：`~/.workbuddy/local_storage/entry_*.info`（`base64(gzip(JSON))`），即 `/v3/config` 的本地落盘。

### 1.2 登录流程（ExternalLinkAuthenticationProvider，CLI bundle @15071xxx）

**无需本地回调服务器**（比 ta3 简单）：CLI 发起 state、打开浏览器、然后轮询服务端。

1. **获取授权状态**：`POST {endpoint}/v2/plugin/auth/state?platform=workbuddy`
   - 头：`X-No-Authorization: true`、`X-No-User-Id: true`、`X-No-Enterprise-Id: true`、`X-No-Department-Info: true`、`X-Domain: copilot.tencent.com`、`Content-Type: application/json`，body `{}`
   - 响应：`{ data: { data: { authUrl, state, ... } } }`（axios 信封 `{data:{data:...}}`）
2. **打开浏览器**：`authUrl` + 追加查询参数 `version={pluginVersion}`（workbuddy 平台再追加 `loginSessionId={会话id}`）；浏览器中用户完成登录（微信扫码/账号密码，服务端托管）
3. **轮询 token**：`GET {endpoint}/v2/plugin/auth/token?state={state}`
   - 头同步骤 1（No-* 系列）；未授权时业务错误码 `RetryFetchToken` -> 继续轮询（间隔 ev 常量，总超时 eI）
   - 成功响应：`data.data = { accessToken, refreshToken, expiresIn, refreshExpiresIn, domain, ... }`；客户端计算 `expiresAt = now + expiresIn*1000`
4. **轮询账号信息**：`GET {endpoint}/v2/plugin/login/account?state={state}`
   - 头：`Authorization: Bearer {accessToken}`、`X-No-User-Id: true` 等
   - 成功响应：`data.data = { uid, nickname, name, avatarUrl, enterpriseId, departmentFullName, ... }`；`RetryFetchAccount` 继续轮询，HTTP 401/403 有限重试
5. **账号列表快照**：`GET {endpoint}/v2/plugin/accounts`（Bearer）-> `data.data = { accounts: [...] }`（多账号/企业账号切换用）

**Token 刷新**（CLI bundle @15075xxx）：
- `POST {endpoint}/v2/plugin/auth/token/refresh`，body `{}`
- 头：`Authorization: Bearer {at}`、**`X-Refresh-Token: {rt}`**、`X-Auth-Refresh-Source: plugin`、`X-Domain: {domain}`
- 响应：新的 `{ accessToken, refreshToken, ... }`（refresh_token 轮转）

**企业账号切换**：`POST {endpoint}/v2/plugin/login/enterprise`（个人）/ `POST {endpoint}/v2/plugin/login/enterprise/{enterpriseId}`（企业），头加 `X-Enterprise-Id`、`X-Tenant-Id`、`X-Refresh-Token`。

**401 处理**（AuthenticationHttpInterceptor，CLI bundle @15035xxx）：响应 401 且 Authorization 与当前 token 匹配 -> 自动登出。业务接口 401 -> refresh 一次后重试。

### 1.3 业务接口鉴权契约

请求拦截器（AuthenticationHttpInterceptor）自动注入：

| 头 | 值 | 说明 |
|---|---|---|
| `Authorization` | `Bearer {accessToken}` | tokenHeader + bearerToken |
| `X-User-Id` | `{account.uid}`（URL 编码） | usernameHeader |
| `X-Enterprise-Id` / `X-Tenant-Id` | `{enterpriseId}` | 企业账号 |
| `X-Department-Info` | `{departmentFullName}` | 企业账号 |
| `X-Domain` | `copilot.tencent.com` | 域名校验 |

`X-No-*` 系列（`X-No-Authorization` / `X-No-User-Id` / `X-No-Enterprise-Id` / `X-No-Department-Info` / `X-Skip-Auth-Interceptor`）用于跳过对应注入（登录轮询端点专用）。

### 1.5 模型请求（调用协议）

CLI bundle `ModelProvider`（@9384xxx-9416xxx）确认：

**baseURL 解析优先级**（`resolveModelBaseURL`）：
1. `models[].url`（官方网关模型**无**此字段；仅自定义模型有）
2. `CODEBUDDY_BASE_URL` 环境变量
3. **默认：`{endpoint}/v2` = `https://copilot.tencent.com/v2`**

**调用端点**：`POST https://copilot.tencent.com/v2/chat/completions` —— CLI 用内置 OpenAI SDK（`new OpenAI({ baseURL, apiKey: accessToken, fetch: axiosToFetchAdapter(), maxRetries: 0 })`），即 **标准 OpenAI Chat Completions 协议，SSE 流式**。

**请求头**（fetch 适配器 + 拦截器注入，桌面端同款集合）：

| 头 | 值 | 来源 |
|---|---|---|
| `Authorization` | `Bearer {accessToken}` | 拦截器 |
| `X-User-Id` | `{uid}` | 拦截器 |
| `X-Domain` | `copilot.tencent.com` | 拦截器（enterpriseHeaders） |
| `X-Enterprise-Id` / `X-Tenant-Id` | 企业账号时 | 拦截器 |
| `X-Product` | `SaaS`（deploymentType） | 桌面端 report 头 |
| `X-Request-ID` / `X-Conversation-ID` / `X-Conversation-Request-ID` / `X-Conversation-Message-ID` / `X-Root-Request-ID` | 每请求生成的 uuid | fetch 适配器 |
| `X-Agent-Intent` | `craft`（会话 mode，`codebuddy.ai/mode`） | fetch 适配器 |
| `X-IDE-Type` / `X-IDE-Name` / `X-IDE-Version` | 客户端标识（如 CLI/desktop + 版本号） | fetch 适配器 |
| `X-Private-Data` | `false`（enableModelOptimization 默认开） | getCustomHeaders |
| `User-Agent` | 客户端 UA | 桌面端注入 |
| `Content-Type` / `Accept-Encoding` | `application/json` / `gzip, deflate` | 常规 |

**请求体**：标准 OpenAI 字段（model / messages / stream / tools / tool_choice / temperature / max_tokens）+ thinking 翻译规则（ThinkingEffortTranslatorRule 等，CLI bundle @8572xxx）：

- `thinkingLevelMap` 档位映射（per-model，如 `kimi-k2-thinking: {low: null, medium: null, high: "high", xhigh: "max"}`）：`reasoning_effort` 按映射转换，映射值为 null 则删除该字段
- `thinkingFormat` 按模型系别（deepseek -> `thinking: {type: "enabled"}`；qwen/zai -> `enable_thinking: true`；openrouter -> `reasoning: {effort}`）
- 默认追加 `reasoning_summary: "auto"`（enableThinking 时）

**响应**：OpenAI SSE chunks（`delta.content` / `delta.reasoning_content` / `delta.tool_calls` 增量 / 尾帧 `usage` / `finish_reason` / `[DONE]`）。

**超时与重试**：连接级错误（ECONNRESET 等）重试 1 次；业务 401 -> refresh -> 重试。

### 1.6 请求时序总览

```
[登录]  POST /v2/plugin/auth/state?platform=workbuddy      (X-No-* 头)
              └─▶ {authUrl, state} ──▶ 打开浏览器授权
         GET  /v2/plugin/auth/token?state={state}          (轮询)
              └─▶ {accessToken, refreshToken, expiresIn}
         GET  /v2/plugin/login/account?state={state}       (Bearer)
              └─▶ {uid, nickname, avatarUrl, enterpriseId}
         GET  /v2/plugin/accounts                          (Bearer，多账号)

[刷新]  POST /v2/plugin/auth/token/refresh                 (X-Refresh-Token + Bearer)

[目录]  GET  /v3/config                                    (Bearer + X-User-Id + X-Domain)
              └─▶ models[]（50 个，含元数据）+ agents[]（cli -> 12 模型）

[对话]  POST /v2/chat/completions                          (Bearer + 全量网关头，SSE)
```

### 1.7 与 ta3 的同构对比

| 维度 | ta3（已接入） | WorkBuddy（本方案） |
|---|---|---|
| 登录 | PKCE(SM3) 浏览器授权码 + 本地回调服务器 | auth/state + 浏览器 + 服务端轮询（无本地回调） |
| token 形态 | `ide-session-*` 裸值头 | accessToken，`Bearer` |
| 模型列表 | list-organizations + list-assistants（多端点候选） | `/v3/config` 单端点 |
| per-model key | `llm-` 前缀 per-model key | 无（统一 Bearer accessToken） |
| 调用协议 | OpenAI / Anthropic 双协议 | OpenAI 单协议 |
| 工具名伪装 | 必须（ta3 原生工具名映射） | **不需要**（标准 function calling 透传） |
| 系统提示词 | 远端下发 baseAgentSystemMessage | 无远端系统提示词（用当前项目自己的） |
| 风控要点 | X-Call-Source: APP + Electron 同族 UA | Bearer + X-User-Id + X-Domain + 会话追踪头 |

**结论**：WorkBuddy 接入复杂度低于 ta3（无工具伪装、无双协议、无 per-model key 管理），复刻 ta3 的"登录态表 + 目录同步 + 专属 Provider + 5 端点路由"四件套即可。

## 4. 数据模型变更

### 4.1 Provider 表

1. `api_format` 扩展枚举值 **`workbuddy`**（前端下拉同步加选项 "WorkBuddy（腾讯 CodeBuddy）"）。

复用现有字段：
- `name` = 模型 id（如 `deepseek-v4-pro`）

- `api_key` = **占位值 `"__workbuddy_session__"`**（model_key 通道要求非空才走 per-model 构造；真实凭证每次请求前由 session 层换取最新 accessToken）

## 5. 详细设计

### 5.1 认证模块 `app/auth/workbuddy/oauth.py`

模块级登录状态机（对齐 `ta3_oauth` 的 pending/done/failed 状态与前端轮询协议）：

```
start_login(db, provider_id, api_base):
  1. POST /v2/plugin/auth/state?platform=workbuddy   （X-No-* 头 + X-Domain）
     -> {authUrl, state}；记入内存态 {phase: pending, state, authUrl, started_at}
  2. 后台任务（asyncio.create_task）：
     a. 轮询 GET /v2/plugin/auth/token?state=...      （RetryFetchToken 继续）
        -> {accessToken, refreshToken, expiresIn...}
     b. 轮询 GET /v2/plugin/login/account?state=...   （Bearer）
        -> {uid, nickname, ...}
     c. GET /v2/plugin/accounts（可选，拿账号列表）
     d. 成功 -> save_auth 落库，置 phase=done
  3. 返回 {status: "pending", authUrl}（前端打开浏览器 + 轮询 status）

get_login_status(db, provider_id) -> {status, account?, error?}
cancel_login(provider_id) -> 清内存态
```

超时：总 300s（ta3 同量级）；轮询间隔 2s。**无需本地回调端口**（对 ta3 是简化：ta3 要开 localhost 回调 server，WorkBuddy 直接轮询服务端）。

### 5.2 会话与刷新 `app/auth/workbuddy/session.py`

```
load_auth(db, provider_id) -> WorkBuddyAuth | None
save_auth(...) / clear_auth(...)
ensure_token(db, provider_id, api_base) -> str:
  1. 读 access_token；无 -> Ta3AuthError 同款 WorkBuddyAuthError("login_required")
  2. 有 -> 直接返回（不预判过期；CLI 也未做定时刷新，依赖 401 兜底）
refresh_token_once(db, provider_id, api_base):
  POST /v2/plugin/auth/token/refresh
  头: Authorization: Bearer {at}, X-Refresh-Token: {rt},
      X-Auth-Refresh-Source: plugin, X-Domain
  -> 覆盖写 access_token/refresh_token
```
401 -> `refresh` 一次 -> 重试一次（ta3 同款语义，目录同步与对话共用）。

### 5.3 目录同步 `app/auth/workbuddy/catalog.py`

## 6. 与 ta3 的差异要点（实现注意事项）

1. **无本地回调服务器**：ta3 登录要开 localhost 端口收 code；WorkBuddy 只轮询服务端（`auth/token?state=`），实现更简单。
2. **无工具伪装**：ta3 要维护 `ta3_tool_aliases.py` 双向映射；WorkBuddy 直接透传当前项目工具 schema（网关是标准 function calling）。
3. **无 per-model llm-key**：ta3 目录下发 per-model key 且写 Model.api_key；WorkBuddy 统一 accessToken，Model.api_key 只作占位，**真实 token 动态获取**（防过期）。
4. **无远端系统提示词**：ta3 目录带 `baseAgentSystemMessage`；WorkBuddy 用当前项目自己的系统提示词，`workbuddy_meta` 不含 systemMessage。
5. **thinking 参数翻译**：WorkBuddy 网关对 reasoning 模型需要档位映射（`thinkingLevelMap`）与系别格式（deepseek/qwen），比 ta3 的固定 `thinking: {type: enabled}` 多一步 per-model 映射；映射表来源：CLI 内置模型注册表（bundled registry，含 `thinkingLevelMap`/`compat.thinkingFormat`），实现时提取常用 12 个模型建静态表，未知模型走 OpenAI 标准 `reasoning_effort`。
6. **多账号/企业账号**：`/v2/plugin/accounts` 返回多账号（个人+企业）。首期只取当前账号（`lastLogin || accounts[0]`），企业切换（`login/enterprise`）列为后续增强。

## 9. 风险与待验证事项

| # | 风险/未知 | 影响 | 缓解 |
|---|---|---|---|
| 1 | **风控头最低集合未实测**：网关是否强校验 X-IDE-* / UA / X-Agent-Intent | 请求可能 403/风控 | 实现时先发全集头（本方案 1.5 表格），逐步裁剪验证；UA 用 Electron 同族（ta3 经验） |
| 2 | **authUrl 授权页交互形态**（微信扫码/验证码） | 不影响后端轮询设计；影响用户文档截图 | 首次联调时记录 |
| 3 | **token 有效期未知**（expiresIn 未观测到值） | 长会话中断 | 401 -> refresh 兜底已覆盖；必要时加定时刷新 |
| 4 | **`auto` 等路由模型行为**：网关侧动态选型，credits 浮动 | 计费展示不准 | meta 保留 credits 字符串原样展示 |
| 5 | **thinking 档位映射表来源**：内置注册表 22MB bundle 中提取，模型更新需跟进 | 新模型 reasoning 参数可能不生效 | 未知模型回退标准 `reasoning_effort`；映射表独立文件便于维护 |
| 6 | **企业账号**：企业策略可能限制可用模型（member-custom-model-policy） | 同步结果与个人号不同 | 首期支持个人账号；企业端点已记录（login/enterprise）留作增强 |
| 7 | **网络连通性**：copilot.tencent.com 需公网可达；桌面端日志显示走本机代理（127.0.0.1:7897） | 部署环境需出网 | httpx 默认走系统代理（trust_env），与 CLI 行为一致 |
| 8 | **合规**：逆向接入属于非官方客户端行为，账号可能受官方风控 | 封号风险 | 与 ta3 接入同级风险；建议用户用小号验证 |
