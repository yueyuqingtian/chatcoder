# ChatCoder 交互与运行时痛点优化方案

> **文档定位**：本方案不是从代码审计角度做面面俱到的优化清单，而是基于「作为 AI 编程助手真实操作这个项目时」感受到的**直观痛点**，给出可落地的改进方向。每一条都对应我在工作中实际踩到的坑。
>
> **撰写日期**：2026-07-26　**作者**：ChatCoder Agent

---

## 一、痛点总览

在操作本项目的过程中，最强烈的体感痛点按"刺痛程度"排序如下：

| # | 痛点 | 体感影响 | 根因位置 |
|---|------|----------|----------|
| 1 | **工具输出被截断到 3000 字符** | 读大文件/搜全仓被迫分页 N 次，上下文割裂 | `agent_runtime.py:52`、`agent_loop.py:27` |
| 2 | **46 处 `except Exception: pass` 静默吞错** | 排障时根因被掩盖，只能靠"猜"定位问题 | 全仓库 44+ 文件 |
| 3 | **两套 agent loop 实现并存** | 改逻辑前必须先确认"哪套是活的"，认知负担大 | `agent_runtime.py`(1332行) vs `agent_loop.py`(494行) |
| 4 | **工具意图退化检测靠正则硬编码** | 中英混合表述、新动词模式无法识别，模型退化时频繁误判 | `agent_runtime.py:74-89` |
| 5 | **上下文窗口/摘要阈值层层透传** | 配置链路长，出问题难追，token 预算行为不可预测 | `context.py`、`context_memory.py`、`token_counter.py` |
| 6 | **缺少工具调用去重之外的反空转策略** | agent 偶尔在相似步骤间来回打转才被 `DiminishingReturnsDetector` 兜住 | `compaction.py:27` |

下面逐条展开。

## 二、逐项分析与优化建议

### 痛点 1：工具输出 3000 字符硬截断 —— 最痛

**现状**
```python
# agent_runtime.py:52
MAX_TOOL_OUTPUT_CHARS = 3000
```
`fs_read` 一个 1300 行的文件，单次只能看到约 60 行；`fs_grep` 全仓搜索结果动辄上万字符，被拦腰截断后"后半部分有没有匹配"完全未知。我不得不反复调整 `offset/limit` 分页调用，**单次信息获取成本极高**。

**优化建议**

1. **按工具分级阈值**，而非全局一刀切：
   - `fs_read` / `fs_grep` / `terminal_exec`：提升至 **12000–16000** 字符（这些是信息密集型工具，截断即丢失上下文）。
   - `web_fetch`：保持 8000（网页噪音多）。
   - `fs_write` 回执：500 足矣。
2. **截断时保留"结构完整性"**：对 `fs_grep` 结果按"匹配条数"而非"字符数"截断，并明确告知 `已截断，还有 N 条未显示，可用 limit/max_results 收窄`，让模型知道下一步如何收窄而非盲猜。
3. **把阈值做成可配置项**（`settings.tool_output_chars`），而非魔法常量，便于按模型上下文窗口动态调整。

**预期收益**：单次工具调用信息量提升 4–5 倍，分页往返减少 60%+，长文件审查体验质变。

---

### 痛点 2：46 处 `except Exception: pass` 静默吞错

**现状**
全仓库 44 个文件、46 处形如：
```python
except Exception:
    pass
```
集中在 `agent_runtime.py`(8处)、`scheduler.py`(5处)、`context_manager.py`(4处)、`context.py`(3处)。我在排查"MCP 工具加载失败"时，发现 `agent_runtime.py:280` 虽有 `logger.warning`，但更多位置是**纯 pass**，错误现场彻底丢失。

**优化建议**

1. **分批替换**，按风险分级：
   - 高风险（`scheduler`、`context`、`agent_runtime` 主流程）：改为 `logger.exception(...)`，保留完整堆栈。
   - 中风险（工具加载、MCP、skill_scanner 等非阻塞路径）：至少 `logger.warning("xxx 失败", exc_info=True)`。
   - 低风险（启动期兼容性探测）：允许 `pass`，但加 `# noqa: silent-by-design` 注释表明有意为之。
2. **引入 lint 规则**：在 `pyproject.toml`/ruff 配置中启用 `BLE001`（blind-except）+ 自定义检查，禁止新增裸 `except: pass`。
3. **统一错误广播**：关键路径异常通过 `agent_events.broadcast` 推送到前端，让用户可见 agent 卡在哪一步，而非界面静默卡死。

**预期收益**：排障时间从"猜根因"降为"看日志定位"，线上问题复现成本大幅下降。

---

### 痛点 3：两套 agent loop 实现并存

**现状**
- `agent_runtime.py`（1332 行）：实际在用，含 MCP 注入、目标延续提示、纯文本退化检测、session 锁等 v1.0 特性。
- `agent_loop.py`（494 行）：文件头注释自称"v2 重构提取"，但**未被主调度链路引用**，属于停滞的重构尝试。

每次我想修改 agent 推理逻辑，第一步必须先 grep 确认"哪套是活的"，这是纯认知损耗。

**优化建议**

1. **立即明确主权**：在 `agent_loop.py` 顶部加 `# DEPRECATED: 见 agent_runtime.py，本文件为未完成的重构，勿在此修改` 横幅注释，避免后续协作者误改。
2. **中期收敛为一套**：以 `agent_runtime.py` 为基线，将 `agent_loop.py` 中确实更优的部分（如 `_truncate_args`、更简洁的 `AgentOutput` 结构）回流，然后删除 `agent_loop.py`。
3. **补一条回归测试**：`test_intent.py` 已覆盖 `_detect_tool_call_intent`，应扩展为对主 loop 的端到端冒烟测试，防止重构期行为漂移。

**预期收益**：消除"两套实现"的认知税，后续所有 agent 逻辑修改成本减半。

---

### 痛点 4：工具意图退化检测靠正则硬编码

**现状**
```python
# agent_runtime.py:79-84
_INTENT_VERBS = [
    "让我读取", "让我查看", "让我审", "让我先读", ...
    "let me read", "let me check", ...
]
```
模型一旦用"我来看看这个文件"、"帮我看下"等未收录表述，正则匹配失败，退化检测失效，agent 进入无效纯文本输出循环，靠 `_MAX_TEXT_RETRIES=3` 兜底才勉强恢复。

**优化建议**

1. **从"动词白名单"转向"结构特征检测"**：判断 content 中是否出现「文件路径 + 行号」「命令行前缀」「`tool(arg)` 模式」等结构化信号，而非枚举自然语言动词。动词集合永远追不上模型的表述多样性。
2. **让模型自检**：在 system prompt 中约定"若你打算调用工具但未生成 tool_calls，请在末尾输出 `[INTENT: tool_name]` 标记"，检测器优先识别该标记，正则作为兜底。
3. **失败时反馈给模型**：检测到退化后，注入的引导消息应**引用模型刚才的具体输出**（"你刚才写了 '我来看看 x.py'，请改用 fs_read 工具调用"），而非泛泛提示，纠正命中率更高。

**预期收益**：退化检测召回率从"取决于动词表完整度"提升到结构信号驱动，空转步数减少。

---

### 痛点 5：上下文窗口/摘要阈值层层透传

**现状**
`context_window` 从 `Model.context_window` → `get_agent_context_window()` → `build_agent_context()` → `maybe_summarize_main_session()` → `MAIN_SUMMARIZE_RATIO=0.15` ... 链路极长。`context_memory.py` 注释列了一堆 ratio，但实际触发行为难以预测。我在长会话中遇到"突然摘要了"却不知道为何触发。

**优化建议**

1. **集中化预算配置**：把所有 ratio/threshold 收敛到 `settings` 的一个 `ContextBudget` 数据类，注释清楚每个 ratio 的含义和触发后果，单一真相源。
2. **摘要事件可观测**：每次触发摘要时，通过 `logger.info` 输出 `{session_id, trigger: "auto_compact", before_tokens, after_tokens, ratio}`，并在前端 task card 提示"上下文已压缩"，让用户和开发者都能看到"为什么压了"。
3. **提供 dry-run 预览**：新增管理端接口 `GET /sessions/{id}/context-preview`，返回当前消息列表 + 预计是否触发摘要 + 压缩后估算 token，便于调试。

**预期收益**：上下文行为从"黑盒"变"白盒"，长会话稳定性可观测、可调优。

---

### 痛点 6：反空转策略偏弱

**现状**
`DiminishingReturnsDetector`（`compaction.py:27`）依赖 `max_idle_steps=5`、`similarity_threshold=0.85`，要连续 5 步空转才触发。实际体感是 agent 已经在"第 2、3 步"就开始打转，但检测器要等到第 5 步才介入，浪费 token 和时间。

**优化建议**

1. **引入"步效信号"**：每步记录 `是否有新工具调用 / 是否产出新 artifact / 工具结果是否与上步不同`，连续 2 步无任何新信号即提前预警（注入"你似乎在重复，请确认目标是否达成"提示），不必等满 5 步。
2. **工具调用图谱去重**：`_called_tool_keys` 已做参数级去重，可扩展为"工具+参数哈希+结果哈希"三元组去重，若结果也相同则直接跳过执行，复用上步结果。
3. **暴露空转计数到前端**：在 task card 显示 `空转步数: 2/5`，让用户感知到 agent 状态，必要时手动中断。

**预期收益**：空转检测从"事后兜底"前移为"事中预警"，平均浪费步数减少 40%+。

## 三、落地优先级

按"投入产出比 × 刺痛程度"排序，建议如下迭代：

| 阶段 | 任务 | 预估工作量 | 收益 |
|------|------|------------|------|
| **P0 立即做** | ① 工具输出阈值分级 + 可配置化 | 0.5 人日 | 单次信息量 ×4，体感最直接 |
| **P0 立即做** | ③ 给 `agent_loop.py` 加 DEPRECATED 横幅 | 0.1 人日 | 消除认知税，零风险 |
| **P1 本周** | ② 高风险路径吞错替换为 `logger.exception` | 1 人日 | 排障效率质变 |
| **P1 本周** | ⑥ 空转检测前移到 2 步预警 | 0.5 人日 | 减少 token 浪费 |
| **P2 下个迭代** | ④ 退化检测改结构信号 + 模型自检标记 | 1.5 人日 | 提升退化召回率 |
| **P2 下个迭代** | ⑤ 上下文预算集中化 + 摘要可观测 | 2 人日 | 长会话可调试 |
| **P3 中期** | ③ 收敛两套 agent loop 为一套 | 3 人日 | 长期维护成本下降 |

## 四、一句话总结

> 这个项目最大的问题不是功能缺失，而是**运行时行为不可观测 + 信息获取被人为限流**。把工具输出截断放开、把吞掉的错误吐出来、把两套 loop 收敛成一套，三项做完，作为 agent 操作这个项目的体验会有质的飞跃。
