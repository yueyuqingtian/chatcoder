## 一、总体判断

项目已经具备功能丰富的本地 AI 编码工作台形态：项目和会话管理、流式消息、工具审批、轮次审核与回滚、多供应商和多凭据、子代理、工作流、Git/worktree、终端、浏览器和电脑操控、记忆索引、定时任务、桌面更新均有实现与不同程度的测试。

当前主要短板在于功能交界处的可靠性：REST 快照与实时事件竞争、操作提交与服务端确认脱节、定时任务排期和执行结果混写，以及源码开发、桌面运行、发行构建三种环境的配置不一致。建议下一阶段先收敛这些问题，再增加更多功能入口。

正面基础包括：前后端分层、共享类型、公共 UI 组件和设计检查、SQLite WAL 与单写者、消息流虚拟化、断线重放、更新下载测试、分级后端测试。这些机制已经存在，后续应优先补齐边界条件，避免推倒重写。

### 定向复现方法与结果

- **cron 解析**：提取当前源文件的 AST，在独立子进程执行 `parse_cron('50-10 * * * *')`，0.5 秒未结束后终止子进程。未向真实服务发送可能卡死的请求。
- **预览算法**：从 2026-10-29 12:00 UTC 开始，按当前路由的游标推进方式计算每分钟表达式，得到 `12:01、12:03、12:05`。
- **定时写入**：执行原函数 AST，以内存假会话替代数据库，确认空字符串更新成功；确认完成回写会把原为 `13:00` 的新排期覆盖成快照中的 `12:01`。这验证了写入逻辑，未模拟真实调度并发。
- **侧会话竞争**：转译当前 sideChat.ts，使用受控 REST Promise 和模拟 WebSocket。先接收消息 id=2，再让旧快照返回空数组，消息列表从 `[2]` 变成 `[]`。模拟传输不交付审批时，本地审批队列仍被清空。
- **本地通道边界**：用仅挂载当前 WebSocket 路由的进程内 FastAPI TestClient，从 `https://untrusted.invalid` Origin 无凭据连接 `/ws/global` 并发送宿主登记，收到 `browser.host.welcome`。没有连接正在运行的桌面服务，也没有执行浏览器操作。
- **开发端口**：用 esbuild 注入 `DEV=true` 转译当前 API 客户端，模拟 fetch 捕获到 `http://127.0.0.1:12973/api/projects`，与 README 指定的开发后端 8000 不一致。

## 三、重点 Bug 和风险

“已复现”指上文限定的隔离复现；“代码确认”指触发条件和错误路径明确，但未做桌面端端到端验证；“条件风险”需要特定配置或环境，不能表述成已经发生的事故。

### B01 · P0 · 倒序 cron 区间可能卡死服务（已复现）

- 位置：`server/app/services/scheduled_service.py:121-130,152-156`；调用入口 `server/app/gateway/routers/scheduled.py:90-97`。
- 触发：输入 `50-10 * * * *`。递增循环无法到达较小终点，普通字段又没有环绕逻辑。
- 影响：异步路由同步执行无界循环，同一事件循环可能停止响应，集合还会持续消耗内存。
- 建议：先校验端点，用有界序列实现允许的环绕语义；不支持的倒序范围直接拒绝；同时检查环绕步长处理。
- 验收：倒序、越界、周日 0/7、环绕步长均在有限时间内返回；校验期间其他接口能正常响应。

### B02 · P1 · 本地服务缺少可信客户端边界（握手已复现，其余代码确认）

- 位置：`server/app/gateway/ws.py:204-246`；`server/app/orchestration/browser/bridge.py:56-90`；`electron/main.cjs:202-205`；`server/app/main.py:316-323`。
- 现状：WebSocket 不校验身份和 Origin；任意兼容登记可进入宿主选择。桌面启动虽明确监听 `127.0.0.1`，同时开启 `CORS_ALLOW_ALL=true`；可访问的 HTTP 业务路由也没有统一身份认证层。
- 影响：本机端口可达时，未受信任客户端有机会订阅事件或登记宿主；恶意网页访问本地服务的风险还取决于浏览器网络策略。不能将回环监听视为应用身份校验。
- 建议：建立 HTTP/WS 一致的随机启动凭据与来源策略，安全传递给可信渲染进程；限制宿主登记。直接运行后端时默认监听地址也应收敛（当前配置默认 `0.0.0.0`）。
- 验收：未知来源、缺少凭据和伪造宿主均被拒绝；桌面、开发模式、重连及后台会话仍正常。

### B03 · P1 · 断线提交审批或回答可能静默丢失（逻辑已复现）

- 位置：`client/src/api/ws.ts:206-210`；`client/src/store/chat.ts:2369-2398`；`client/src/store/sideChat.ts:321-331`。
- 触发：连接未打开时点击允许、拒绝或提交回答。send 不发送且不报失败，调用方随即删除待处理项与部分草稿。
- 影响：用户看到卡片消失，后端仍等待。主会话重连存在未决项对账，但不能恢复已经清掉的回答；侧会话也缺少同等完整的对账保障。
- 建议：引入待发送/待确认/已完成状态，以服务端确认出队，保留输入并支持幂等重试。
- 验收：提交前后断线、重连、重复点击均不丢答案、不重复处理，前后端等待状态一致。

### B04 · P1 · 旧运行完成会覆盖新排期（写入逻辑已复现）

- 位置：`server/app/services/scheduled_service.py:311-325,337-380`；`server/app/services/scheduler_loop.py:107-129`。
- 触发：运行期间修改 cron，或多轮任务交错结束。领取阶段先推进排期，完成阶段再无条件写入旧快照。
- 影响：新配置被旧结果覆盖，可能产生错误排期或重复领取。
- 建议：排期推进和运行结果分别维护；完成回执不回写排期，或使用版本检查及独立运行记录。
- 验收：长任务中修改 cron、运行逆序结束和手动试跑后，排期仍取最新有效值。

### B05 · P1 · 定时任务可能把失败、中断或等待确认记为成功（代码确认）

- 位置：`server/app/services/scheduler_loop.py:105-110`；`server/app/orchestration/engine.py:1312-1341,1912-1928`。
- 原因：调度器忽略 start_turn 的返回值；执行器部分失败和等待分支正常返回，不抛异常，调度器统一写 `ok`。
- 影响：用户误以为自动化已经完成，难以发现未执行或未完成的任务。
- 建议：按持久化 turn 的终态及非终态映射展示，明确等待用户确认的情况。
- 验收：成功、失败、中断、项目失效、等待确认的状态与真实运行一致。

### B06 · P1 · 空 cron 能保存，并可能阻塞同批任务（写入已复现，批次影响代码确认）

- 位置：`server/app/services/scheduled_service.py:270-288,353-380`。
- 原因：`if cron` 跳过空字符串校验，而字段写入仅排除 None。到期领取在同一事务中逐条计算，坏表达式会使批次异常。
- 影响：一条非法记录可能持续影响其他到期任务。
- 建议：区分字段未提供和提供空值；拒绝空白表达式，对历史坏记录逐条隔离并展示错误。
- 验收：非法更新返回明确错误；插入历史坏数据后其他任务仍能被领取。

### B07 · P2 · 侧会话旧快照覆盖新消息或新运行态（已复现）

- 位置：`client/src/store/sideChat.ts:102-125,175-195,244-263`。
- 触发：REST 请求在途时接收新事件，随后旧结果返回；多个刷新请求也可能反序完成。
- 影响：消息暂时消失，运行标记倒退，用户会以为消息丢失或任务状态异常。
- 建议：按会话和数据类型管理请求代次，并通过事件序号或服务端版本合并快照与增量；单独的请求代次不能解决请求期间收到实时事件的问题。
- 验收：控制响应乱序、实时事件交错和会话切换，最终状态保留最新数据。

### B08 · P2 · 定时预览跳过相邻分钟（已复现）

- 位置：`server/app/gateway/routers/scheduled.py:79-86`。
- 原因：compute_next_run 已寻找严格晚于游标的时刻，路由又额外加一分钟。
- 影响：每分钟规则显示成每两分钟一次；这里确认的是预览错误，没有认定实际调度也跳过。
- 建议与验收：直接使用刚返回的时刻作为下次游标；每分钟规则连续显示相邻分钟，并覆盖日、周与时区边界。

### B09 · P2 · 按 README 启动开发环境会连接错误端口（请求地址已复现）

- 位置：`README.md:153-178,290`；`client/vite.config.ts:12`；`client/src/api/client.ts:60-85`；`client/src/api/ws.ts:71-86,254`。
- 原因：文档和 Vite 代理默认后端为 8000，但开发态 REST 与 WS 绕过代理直连 12973；CHATCODER_BACKEND 也只配置代理。
- 影响：只有 8000 服务时界面连接失败；若 12973 恰有已安装版本实例，开发前端可能连接到另一实例和其数据。
- 建议：统一后端地址来源，开发态默认走同源代理或生成一份统一连接配置；同步修正文档。
- 验收：干净开发环境、自定义端口和已安装桌面版同时存在时，REST、会话 WS、全局 WS 都连接指定开发实例。

### B10 · P2 · Markdown 文件链接缓存跨项目复用（代码确认）

- 位置：`client/src/components/ui/Markdown.tsx:30-37,89-125`。
- 原因：存在性缓存仅以相对路径为 key，忽略 currentProjectId；已有结果没有过期机制。
- 触发：项目 A 的 src/main.ts 不存在，随后查看项目 B 中相同路径的真实文件，仍直接命中 false；反向也会将不存在的文件标成可点击。
- 影响：有效链接不能打开，或点击后面板找不到文件；同项目创建或删除文件后也可能保留旧结果。
- 建议：缓存键含项目标识和规范化路径，增加失效策略；切换项目和路径时正确重置校验状态。
- 验收：两个项目相同相对路径、文件新增删除和项目切换均显示正确。

### B11 · P2 · 源码安装依赖缺少 SQLite 驱动（依赖声明确认，未新建环境安装）

### B12 · P2 · 侧会话引用上下文混入用户问题正文（代码确认）

- 位置：`client/src/store/sideChat.ts:269-299`；`server/app/gateway/routers/turns.py:71-88`；`client/src/components/chat/UserBubble.tsx:17-19`。

## 四、后续优化重点

### 1. 运行状态与操作反馈

将“运行中、等待审批、等待回答、等待确认、失败、中断、完成”形成统一状态口径，主消息流、侧会话、侧栏和自动化共用。操作提交后显示待确认状态，失败时保留草稿和重试入口，避免卡片消失被误认为提交成功。

首要覆盖用户路线：创建项目 → 配置模型 → 发起会话 → 提交审批/回答 → 查看变更 → 审核/回滚，以及运行中切会话、关闭侧面板、断网与恢复。外观调整应放在这些路径稳定后进行。

### 2. 自动化调度

将任务配置、下一次排期、单次执行记录拆开。补足 cron 边界、编辑与执行交错、失败/中断状态、坏记录隔离、错过策略和时区回归。当前测试中没有独立的 cron/调度业务回归文件，现有大量其他测试不能替代这部分覆盖。

### 3. 发布和环境一致性

- 发布前增加前端测试与分级后端测试门禁；当前 release.yml 调用打包脚本，未执行这些测试。
- 统一 npm 构建、正式发布脚本与文档；对干净安装、依赖声明和发行包内容增加验证。
- 修复 `npm run lint` 的悬空入口；将检查工具和配置纳入锁文件，而不是依赖开发机器预装。
- 健康接口和 OpenAPI 当前硬编码 `0.4.0`（`server/app/main.py:310,429`），应明确其是 API 协议版本还是产品版本；产品诊断信息应从根 package.json 的构建元数据派生，便于辨识旧实例。

### 4. 性能：先测量，再针对性拆分

本轮构建主 JS 约 **2135 kB**、gzip **681 kB**；主 CSS 约 **649 kB**、gzip **110 kB**；Stage chunk 约 **693 kB**。这些是构建产物大小，不能直接等同于启动慢或拖拽卡顿。

- `App.tsx` 静态引入设置中心，设置中心进一步静态引入各设置页；可优先评估按设置页拆包。文件树与终端已经 lazy，保留已有成果。
- 明确哪些动态 import 实际仍被其他静态引用纳入同一包；本轮 Vite 对 panel、API 等模块给出了此类警告。
- 在长消息流、并行子代理和右面板拖拽场景测量首屏时间、长任务、帧时间与内存，再调整虚拟化、增量派生和渲染订阅粒度。
- 当前本机缺少 JetBrains Mono 依赖文件，构建留下未解析字体 URL。锁文件已有声明，先在干净 npm ci 环境复查；本轮不能认定正式安装包一定缺字体。

### 5. 维护成本与设计一致性
